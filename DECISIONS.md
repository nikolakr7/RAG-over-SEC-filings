23. ontology_path notation (found while verifying q030/q031: drafted paths were undirected stubs like `Company -PARTY_TO- Agreement`, some with the direction reversed, some free text). Rules: (a) every edge is written with an arrowhead in the ontology's domain -> range direction (`Company -PARTY_TO-> Agreement`, `Filing -FILED_BY-> Company`), never reversed; (b) PARTY_TO always carries `role` (licensor/licensee, acquirer/acquired, plaintiff/defendant, claimant/respondent, collaborator), because direction of a deal lives on roles (#20); (c) Agreement instances carry `type` from ontology.md's list; (d) other properties (dates, status, territory, jurisdiction, office) appear only when the question hinges on them; (e) a path must express the claims in the answer (or required_core when present) as edges, though it need not enumerate every edge the graph could hold (#15 still governs); (f) no free-text paths; instance labels are stable names in parentheses, e.g. `Agreement(HALO-Roche ENHANZE, type: collaboration_license)`. (g) set-valued and aggregation questions may bind a variable and state its result set (`Company(NBIX) -PEER_OF{year: 2025}-> Company(X) <-PEER_OF{year: 2025}- Company(HALO); X = {...}`), which is a pattern, not free text. Verified questions q001-q029 were normalized on 2026-08-16; the sweep over the rest happens at the freeze; until then paths are fixed as questions are touched. (Rejected: leaving stubs and normalizing only in the graph schema later, because a path that does not say who licenses what to whom cannot be checked against the ontology, which was the point of requiring paths.)

31. Leading XBRL junk is stripped from every parsed .txt BEFORE chunking, one time. The strip is prefix-only and pattern-gated (lines that are single tokens, pure numbers or dates, URLs, or carry XBRL markers like xbrli:/iso4217:/us-gaap), stopping at the first line containing a space that matches no junk pattern, so real short-line content further down (Exhibit 21 subsidiary lists) is untouched. Reason: chunking is write-once; embeddings, chunk IDs, and every Phase 3 edge's source_chunk_id derive from the exact text, so text surgery after chunking would invalidate all of them, and junk chunks would sit in the index as retrievable noise. (Rejected: stripping later as cleanup, which re-mints IDs; leaving it in, which embeds tag soup.)
32. Chunk IDs are {accession}#{index:04d}: EDGAR's dashed accession number (already the Filing MERGE key in the ontology) plus a zero-padded index running across the accession's documents in deterministic order (primary document first, then exhibits sorted by filename). Each chunk also stores text_sha256, as an integrity check, never as identity: re-runs verify byte-identical text and fail loudly on drift. The chunker is frozen once the first corpus run is accepted. (Rejected: a global running number, whose meaning depends on corpus processing order; character ranges, whose offsets shift under any future text fix; content hash as identity, which collides identical boilerplate across filings into one ID, destroying which-filing provenance, and silently mints new IDs on drift instead of erroring.)
33. Chunk boundaries: whole lines (the parser emits one paragraph per line) merged greedily to a ~400-token target with an 800-token hard max, tokens counted with the embedding model's own tokenizer (cl100k_base); a single line over the max is split at sentence boundaries, never mid-sentence; NO overlap between chunks. Reasons: seam-aligned chunks are topically coherent, so their one vector stays sharp (a chunk gets exactly one vector; averaging topics dilutes it), and small chunks lose antecedents ("the Company", "we") that filings lean on. Overlap is rejected specifically because the citation validator resolves quotes to chunk IDs: a sentence living in two overlapping chunks gives one quote two valid IDs and poisons provenance; the marginal boundary-recall gain is not worth an ambiguous provenance key. Two boundary refinements were added during acceptance testing (the test: every benchmark evidence-quote fragment must land inside one chunk): a short heading-like trailing line (capitalized, no digits, no closing punctuation) is carried forward so names/section heads stay with the paragraph they introduce, and no boundary may fall before a line starting lowercase or with a digit/currency fragment, since the parser splits amounts like '$410.0 million' across lines and those glue backward. Accepted at 288/290 fragments contained (99.3%), the 2 stragglers split across adjacent chunk pairs, 0 missing; the citation validator should fall back to adjacent-pair matching.
34. HNSW index: M=16, ef_construction=64 (pgvector defaults), hnsw.ef_search=80 set as the database default; built by load_pgvector.py after the COPY (drop, bulk load, build). Measured by src/vectorstore/hnsw_sweep.py: index recall@10 against a numpy exact-scan ground truth, the 80 benchmark questions as queries (question text only, label-free), tie-aware because 1,638 chunks share a byte-identical vector. Sweep of 3 builds x 6 ef_search values: recall rises steeply then flattens (default build 0.82 at ef_search 10, 0.96 at 40, 0.99 at 80, 0.995 at 320), at 1 to 6 ms p50 vs 81 ms for the exact scan; M=8 stays far behind at every ef_search (0.976 even at 320: a longer shortlist cannot create links the graph lacks). Build-to-build variance is material and must be quoted with any number: HNSW assigns layers randomly, and six identical builds scored 0.973 to 0.989 at ef_search 80 (mean 0.981), so the M=32 gain at ef_search 80 (0.994) is within build noise and did not justify double the build time. ef_search=80 is also the planner's ceiling here: from 100 up it silently chose the seq scan for all 80 queries (recall 1.0 at exact-scan latency, which reads as a perfect index); the sweep forces the index and asserts the plan at every setting, and any change to the corpus or these parameters needs the unforced plan re-checked. Index size is 128 MB for every M: at 1536 dims one ~6 KB vector fills most of an 8 KB page, so links ride in the leftover space. Builds run serially with maintenance_work_mem 1GB because a parallel build puts that memory in /dev/shm, which Docker caps at 64 MB. (Rejected: M=32/ef_construction=128, gain within build noise; ef_search 160+, needs enable_seqscan tricks to use the index for about half a point; the exact scan with no index, fine at 17k rows but linear in corpus size, and the goal is the system that scales. Not yet known: whether index misses ever hit a gold evidence chunk; retrieval recall with exact scan vs index answers that next. M and ef_construction moved together in the sweep, so their separate effects are unmeasured.)
